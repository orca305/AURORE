# 생성형 답변 방식 — 2026-11-21

## 왜 바꿨나
기존 방식은 "후보 조문 중에서 고르고, 고른 한 조문의 한 항만 풀어 쓴다"였다. 그래서 (1) 조문을 다시 읽어 주는 수준의 답이 나오고,
(2) 모델이 아는 조문(민법 제759조, 유류분 등)도 후보에 안 들면 못 찾고, (3) 원문에 없는 말은 전혀 못 해서 실질적인 도움이 안 됐다.
프로젝트 원칙(AGENTS.md)은 "인용문을 원문과 대조한다"이지 "설명을 원문 문장으로 제한한다"가 아니다.

## 구조 (기본값, `AURORE_ANSWER_MODE=classic` 이면 예전 방식)
1. **조문 짚기** `/legal/propose`: 모델이 적용 법령·조문을 직접 짚는다(법률 질문이 아니면 `legal=false` → 답하지 않음).
2. **DB에서 직접 찾기**: 법령 이름을 정식 명칭으로 맞춘 뒤(약칭 표 + 비슷한 이름, `law-names.ts`) 그 조문을 후보 맨 앞에 넣는다.
   번호가 DB에 없으면 같은 법 안에서 질문과 가장 가까운 조문으로 대신한다. 이 단계는 질문 분석·어휘/의미 검색과 **동시에** 시작한다.
3. **답변 작성** `/legal/answer`: 근거 조문(후보 6개 + 핵심 조문의 시행령·벌칙·참조·앞뒤 조문 최대 5개, 인용 법령 일치 검사를 통과한 것만)을 받아
   결론 → 이렇게 해 보세요 → 알아 둘 내용 → 주의할 점 → 확인해 보세요를 쓴다. 각 항목의 근거 번호(refs)를 밝힌다.
4. **표시**: 근거 있는 항목은 "— 근거: 법령 제N조", 없는 항목은 "(일반 안내)", 원문에 없는 숫자가 있는 항목은 버리지 않고 "(숫자는 원문으로 확인되지 않았어요)".
   단정 표현·원문에 없는 조문 번호·범위 밖 근거 번호는 지운다. "20분의 1 → 5%" 같은 단순 환산은 허용한다. 끝에 근거 조문 목록과 도움 받을 곳(고정 연락처 표 `help-contacts.ts`, 번호는 사람 검수 필요).
5. 생성형이 실패하면 예전 선별·해설 방식으로 넘어간다.

## 모델
- **Haiku(`claude-haiku-5-5`) 고정**: `local-dev/.env` 의 `ANTHROPIC_API_KEY` 가 있으면 시작 스크립트(`Set-AuroreExternalEnv`)가 AI 서버 프로세스에만 전달한다. 외부로는 마스킹한 질문과 공식 법령 원문만 나간다(동의 문구는 아직 없음).
- **예산 소진 시 로컬 자동 전환**: 크레딧 부족·인증 오류(쿨다운 15분), 과부하(1분), 네트워크(30초)면 같은 요청을 로컬 12B가 대신 처리한다. 끄기 `AURORE_EXPLAIN_FALLBACK=0`.
- 질문 분석(검색어·법령 이름)과 임베딩(bge-m3)은 로컬이 한다.

## 함께 고친 버그
- **원문 캐시가 처리 도중 필요한 법령 원문을 밀어내 그 법령 후보가 통째로 빠지던 문제**(민법·형법 질문에서 국제사법 등이 대신 인용되던 원인). 이전 측정에도 영향이 있었을 수 있다.
  질문에 필요한 원문을 처리 시작 시점에 따로 잡아 두도록 고쳤다. 캐시는 개수가 아니라 용량(`AURORE_EVIDENCE_CACHE_MB`, 기본 64MB 어림)으로 관리하고
  자주 쓰는 21개 법령은 상시 유지한다(`AURORE_EVIDENCE_PIN=0` 으로 끔, `evidence-cache.ts`).
- 병합 사건 판례의 사건번호 불일치로 수집이 멈추던 문제(`capture-law-samples.mjs`).

## 알려진 한계
- "일반 안내"는 약 28%. 법에 없는 실무 조언이 대부분이지만, 판례가 필요한 내용(과실비율, 손해배상 범위)은 판례 수집·연결 전까지 근거를 달 수 없다.
- 평가 정답은 법령 이름 단위다(조문 단위 정답 없음). 표본이 작아 1~2건 차이는 우연일 수 있다.
- 답변은 응답이 끝난 뒤 한 번에 나간다(결론부터 흘려 보내기는 작업 처리 구조 변경이 필요해 미적용).
