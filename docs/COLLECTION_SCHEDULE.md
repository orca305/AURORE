# 수집·백업 예약 실행과 실패 감시

2026-11-16 구현 기준. 별도 Node 실행기가 기존 법령·판례 수집 도구를 호출한다. 새 라이브러리·DB 테이블·DB 트리거는 추가하지 않았다. 수집 결과는 검토 자료이며 자동 DB 반영을 하지 않는다.

## 현재 노트북 설정

법령 수집은 한국 시간 매일 03:00으로 활성화했다. 최초 수집 기준일은 2026-11-15이고, 최초 실행에서 해당 날짜의 준비를 완료했다. 다음 예약은 2026-11-17 03:00이다. 한 번에 최대 7일을 처리하는 기존 수집기를 사용한다. 별도로 실행한 감시 프로세스가 켜져 있을 때 동작한다.

DB 백업은 한국 시간 매일 02:00으로 활성화했다. 새 백업의 복원 검증 후 관리 대상 묶음을 7일 기준으로 정리한다. 자세한 조건은 [백업·복구 안내](BACKUP_RESTORE.md)를 따른다.

판례 예약은 대상 묶음을 아직 지정하지 않아 비활성이다. 판례 자동 수집 대상은 설정에 명시한 최대 10개 묶음만 사용하며, 검색 후보 폴더 전체를 임의로 순회하지 않는다. 묶음에 기존 `queue.json`이 있으면 이어 받고, 없으면 검증한 `input.json`으로 수집을 시작한다. 이미 완료된 판례는 다시 받지 않는다. 회차당 최대 20개를 처리하며 남은 자료는 15분 뒤 계속한다. 새 판례 검색 목록을 주기적으로 다시 생성하는 기능은 포함하지 않는다.

## 실행 방법

저장소 루트에서 실행한다. `local-dev/collection-scheduler/config.json`과 실행 상태 파일은 Git에서 제외한다. 구성 예시는 `local-dev/collection-scheduler.example.json`이다. 설정이 없으면 모든 예약은 기본 비활성이다.

```powershell
# 상태만 조회: API 호출·파일 변경 없음
node backend/tools/collection-scheduler.mjs --status

# 현재 예약 회차를 한 번 처리
node --env-file=local-dev/.env --use-system-ca backend/tools/collection-scheduler.mjs

# 1분 간격으로 확인하는 실행기 가동
node --env-file=local-dev/.env --use-system-ca backend/tools/collection-scheduler.mjs --watch

# 종료된 로컬 실행기의 점유가 남은 경우, 확인 후 재개
node --env-file=local-dev/.env --use-system-ca backend/tools/collection-scheduler.mjs --watch --recover-lock
```

첫 위치 인자로 다른 예약 저장소를 지정할 수 있다. 관리자 API도 같은 저장소를 보려면 `AURORE_COLLECTION_SCHEDULER_DIR`를 같은 절대 경로로 설정한다. 법령 수집 기록 경로는 관리자 법령 저장소 설정과 맞추고, 판례 대상 폴더는 관리자 판례 저장소 안에서 사용한다. 예약 저장소와 수집 원문 저장소를 같거나 서로 포함되는 경로로 설정하지 않는다.

현재 Windows 작업 스케줄러나 부팅 자동 시작은 등록하지 않았다. PC를 재부팅하면 위 `--watch` 명령으로 실행기를 다시 시작해야 한다. 다른 컴퓨터로 옮길 때 로컬 설정의 절대 경로도 해당 PC에 맞춘다. 전경에서 실행한 감시기는 Ctrl+C로 종료할 수 있다. 강제 종료로 점유가 남으면 프로세스 종료를 확인한 뒤 복구 옵션을 사용한다. 실행 중이거나 다른 기기의 점유, 손상된 점유는 자동 회수하지 않는다.

## 재시도와 상태

예약은 한국 시간 기준의 가장 최근 일일 회차를 처리한다. 실행기가 꺼져 있었으면 다음 기동 시 밀린 수집을 최근 회차에 이어 받는다. 수집 기준일은 기존 완료 기록에서 결정되므로 단순히 빠진 예약 횟수만큼 같은 요청을 반복하지 않는다.

- 정상 완료한 회차는 중복 실행하지 않는다. 두 실행기를 동시에 켜도 하나만 점유한다.
- 실패는 1시간 간격으로 한 예약 회차에 최대 3회 시도한다. 3회 실패하면 다음 일일 회차까지 멈춘다. 다음 회차에서도 실패하면 연속 실패 수는 이어진다.
- 밀린 자료가 남으면 실패로 세지 않고 15분 뒤 계속한다. 정상 처리하면 연속 실패 수를 초기화한다.
- 실패한 수집의 기존 체크포인트는 보존한다. 대상 수집기에 종료된 점유가 남은 경우 자동으로 강제 회수하지 않는다. 대상 도구에서 상태 확인·복구 후 재개한다.
- 예약 설정을 바꾸면 해당 작업의 설정 지문이 바뀌어 다음 확인 때 새 설정으로 평가한다. 같은 자료의 중복 저장은 기존 수집 체크포인트가 막는다.

관리자의 **수집·백업 예약**에서 가동 여부, 최근 상태 갱신, 작업 상태·최근 정상 처리·연속 실패·다음 처리 시각을 확인한다. 갱신이 2분 이상 늦으면 처리 중 또는 응답 지연으로 표시한다. 법령 준비 내부 단계는 동기식 외부 프로세스를 사용하므로 긴 작업 중에도 지연 표시가 나올 수 있다. 지연 자체를 프로세스 사망으로 단정하지 않는다.

설정 손상이나 상태 파일 손상은 화면에서 확인 필요로 표시하고 실행을 거부한다. 상태 파일은 완성한 임시 파일을 원자적으로 교체하며, 오류 기록은 고정 코드만 남긴다. 백업 생성·복원 검증 실패는 기존 백업을 보존하고, 정리 대상 확인에 실패하면 정리 실패로 표시한다. 관리자 응답에는 로컬 경로·호스트·프로세스 번호·점유 토큰·원문 오류를 전달하지 않는다. 이메일·메신저 등의 외부 알림은 전송하지 않는다.

## 검증

가상 시계·합성 수집 결과로 한국 시간 경계, 중복 실행 차단, 다운타임 후 재개, 실패 재시도 한도, 밀린 자료 재개, 설정 변경, 잘못된 상태 거부를 검사했다. 별도 감시 프로세스를 강제 종료해 점유가 남는 상황과 명시적 복구도 재현했다. 실제 법령의 최초 날짜 준비를 실행했으며 DB 게시나 판례 자동 수집은 하지 않았다. 관리자의 실패 감시 화면은 임시 DB·합성 실패 기록으로 검증한다.
