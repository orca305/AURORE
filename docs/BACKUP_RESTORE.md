# 개발 DB 백업·복구 검증

2026-11-16 실제 PostgreSQL 17 개발 DB에서 검증했다. 백업 대상은 `127.0.0.1:5433/aurore_dev_check`이며, 기존 DB에 복원하거나 데이터를 덮어쓰는 기능은 제공하지 않는다.

## 검증 결과

- 전체 32개 public 테이블, 492개 행의 내용 지문이 백업 시점과 복원본에서 일치했다. 테이블 수에는 Prisma 마이그레이션 관리 테이블을 포함한다. 설계상 40개 테이블의 구현 완료를 뜻하지 않는다.
- 컬럼·인덱스·제약조건·확장·번호 생성 정의·프로젝트 함수·트리거의 구조 지문을 비교했다.
- 자동 번호 생성기 18개의 다음 값이 복원 데이터의 최대 번호보다 큰지 확인했다. 검사 중 실제 다음 번호를 소비하지 않는다.
- 실제 Prisma와 법규 서비스로 법령 1건, 판례 3건, 시행본 6개의 조회를 확인했다. 사용자 대화·계정 정보는 출력하지 않았다.
- 검증에 사용한 별도 DB와 컨테이너 안의 임시 덤프는 확인 후 정리했다. 기존 서비스 DB에는 쓰기를 실행하지 않았다.

## 실행

Docker의 개발 PostgreSQL과 백엔드 빌드 결과가 필요하다. 저장소 루트에서 실행한다.

```powershell
# 처음 실행하거나 백엔드 코드가 변경된 경우 먼저 backend에서 pnpm build
node --env-file=local-dev/.env backend/tools/verify-db-backup.mjs

# 이미 만든 백업을 다시 임시 DB에 복원해 검증
node --env-file=local-dev/.env backend/tools/verify-db-backup.mjs --verify C:/Users/wjb/AppData/Local/AURORE/backups/백업묶음이름

# 종료된 이전 백업 프로세스의 점유가 남았으면 상태를 확인한 뒤 복구
node --env-file=local-dev/.env backend/tools/verify-db-backup.mjs --recover-lock
```

기본 위치는 Windows의 `%LOCALAPPDATA%/AURORE/backups`다. 현재 노트북에서는 `C:/Users/wjb/AppData/Local/AURORE/backups`이므로 C 드라이브 공간을 사용한다. 데스크탑으로 옮긴 뒤 `AURORE_BACKUP_DIR` 또는 첫 위치 인자에 원하는 개인 백업 디렉터리의 절대 경로를 지정할 수 있다. 집의 8TB 디스크를 현재 노트북에서 사용한다고 가정하지 않는다.

각 묶음에는 `database.dump`, `manifest.json`, `verification.json`이 들어간다. 덤프에는 계정 인증 자료와 대화·사건·정제 Markdown 등 DB 전체 내용이 포함되므로 사용자 개인 저장소에 보관하고 Git에 올리지 않는다. 메타데이터에는 원문 대신 구조·내용 해시와 건수만 저장한다. 검증 결과 파일은 성공 여부와 집계·조회 결과만 담는다. 덤프의 암호화를 추가한 것은 아니며, 사용자 개인 디렉터리의 접근 권한을 사용한다.

## 백업과 검증 방식

1. 원본 연결은 읽기 전용 반복 읽기 트랜잭션을 사용한다. 진행 중인 마이그레이션이 있으면 중단한다.
2. 원본에서 내보낸 같은 스냅샷을 `pg_dump -Fc --snapshot`에 전달한다. 그 시점의 테이블 행을 PK 순서대로 작은 묶음으로 읽어 SHA-256 지문을 계산한다.
3. 덤프를 사용자 개인 저장소로 복사하고 파일 크기·SHA-256과 원본 데이터 지문을 기록한다.
4. 로컬에 보관된 덤프를 다시 읽고, 임의 이름의 새 임시 DB에 `pg_restore --single-transaction --exit-on-error`로 복원한다. 복원 대상 이름이나 기존 DB를 사용자가 지정하는 옵션은 없다.
5. 전체 내용·구조·번호 생성 상태를 비교하고 Prisma 조회를 수행한다. 성공과 실패 모두 임시 DB를 정리하며, 검증 실패는 성공으로 표시하지 않는다.

구조 비교에서는 삭제 컬럼의 물리적 번호 공백을 제외하고 실제 남은 컬럼 순서를 유지한다. PostgreSQL 복원 과정에서 같은 `varchar[] → text[]` 변환이 각 문자열 항목으로 이동하는 표현 차이도 제한적으로 정규화한다. 문자열 값 변경, 제한 길이가 있는 자료형 변환, 다른 식까지 같다고 간주하지 않는다. 이에 대한 회귀 검사를 포함한다.

공식 동작의 근거는 [PostgreSQL 17 pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)와 [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)다.

## 실패 처리와 제한

손상된 아카이브·메타데이터, 구조 차이, 같은 행 수의 내용 변경, 잘못된 번호 생성 상태, 허용하지 않은 원본·복원 대상은 실패로 처리한다. 원문 오류·명령어 진단·연결 비밀번호를 결과에 넣지 않는다. 재검증이 실패하면 해당 묶음의 검증 결과 파일도 실패로 갱신한다. 기존 덤프를 고치거나 덮어쓰지 않는다.

백업 생성 중에는 저장소 전체를 점유하므로 두 백업을 동시에 생성하지 않는다. 실행 중이거나 다른 기기의 점유는 회수하지 않는다. 강제 종료 뒤의 임시 파일·실패한 묶음은 정상 검증된 백업으로 간주하지 않는다. 오류를 진단하며 만든 이전 미검증 묶음도 이 구분에 해당한다.

이번 검증은 같은 PostgreSQL 17 컨테이너의 독립 DB에 복원하는 훈련이다. 다른 PC·다른 스토리지·실제 장애 후 복구를 검증한 것은 아니다. PostgreSQL 역할·비밀번호·테이블스페이스 등 클러스터 전역 설정, `.env`, Docker 구성, 수집 중인 파일·실행 기록은 DB 덤프의 복구 범위와 구분한다. 첨부 정제 Markdown과 이미 게시한 법령·판례 원문은 DB에 저장되어 이 백업에 포함된다. 사용자 업로드 원본을 별도 파일로 추가 복제하지 않는다.

현재 public 스키마의 PK가 있는 일반 테이블을 비교한다. PostgreSQL Large Object 사용 시에는 이 도구가 중단한다. 대규모 서비스용 증분 백업·WAL 기반 시점 복구 도구는 아니다. 실제 운영 복원은 예전 세션·삭제·파기 상태의 재등장 문제를 검토한 뒤 별도 절차로 수행해야 한다. 복원본을 웹이나 AI 작업기에 연결하는 기능은 제공하지 않는다.

## 예약 백업과 7일 보관 회전

백업은 기존 예약 실행기에 연결했고 노트북에서 한국 시간 매일 02:00으로 활성화했다. 현재 회차를 처음 실행해 새 백업 생성과 전체 복원 검증에 성공했다. 다음 예약은 2026-11-17 02:00이다. 실행기가 꺼져 있으면 기동할 때 최근 회차를 처리한다. Windows 부팅 자동 시작은 등록하지 않아 PC 재부팅 후 실행기를 다시 켜야 한다. 명령은 [예약 실행 안내](COLLECTION_SCHEDULE.md)를 따른다.

로컬 예약 설정의 `backup`에는 `enabled`, `dailyAt`, `root`를 지정한다. `root`는 개인 백업 저장소의 절대 경로다. 예시의 `USER`는 실제 Windows 사용자 폴더로 바꿔야 한다. 이전 설정에 `backup`이 없어도 오류 없이 비활성으로 해석한다. 관리자 **수집·백업 예약**에서 최근 검증 결과, 정리한 묶음 수, 연속 실패와 다음 실행을 확인한다. API 응답에 백업 경로나 덤프 내용은 넣지 않는다.

새 백업을 만들 때 다음 순서로 7일 회전을 수행한다. 기존 백업의 재검증만 수행하는 `--verify`는 회전을 실행하지 않는다.

1. 새 덤프와 메타데이터를 디스크에 저장하고 복원 검증을 완료한다.
2. 보존할 새 묶음의 파일 해시와 검증 결과를 다시 확인한다. 새 묶음은 최근 24시간 안에 만들어지고 검증된 것이어야 한다. 검증 실패·오래된 검증 기록·파일 변조가 있으면 정리하지 않는다.
3. 저장소 바로 아래의 도구 전용 이름 형식에 맞는 묶음 중 생성부터 정확히 7일(168시간) 이상 지난 것만 찾는다. 폴더 이름의 시각과 메타데이터의 생성 시각도 대조한다. 방금 만든 묶음과 7일 미만 묶음은 보존한다.
4. 경로·일반 파일 여부·아카이브 해시·관리용 메타데이터를 확인하고 해당 파일만 정리한다. 재귀 삭제를 사용하지 않는다. 알려진 형식의 비어 있는 오래된 묶음 폴더도 정리할 수 있다.

사용자 메모 등 예상 밖 파일, 변조되거나 불완전한 아카이브, 저장소 밖으로 향하는 링크는 보존하고 확인 필요로 집계한다. 정리 대상 중 확인하지 못한 묶음이 있으면 예약 작업에 정리 실패를 표시한다. 백업 생성·검증 실패 시 기존 묶음을 삭제하지 않는다. 정리 도중 오류가 나도 새 검증 백업은 유지한다. 부분 정리 흔적 등 확인 불가능한 오래된 자료는 수동 점검이 필요할 수 있으므로, 모든 파일이 반드시 7일에 제거된다는 보장은 아니다.

현재 저장소의 실제 묶음은 모두 7일 미만이어서 첫 예약 실행의 삭제 건수는 0개였다. 만료 경계, 새 검증 실패 시 보존, 알 수 없는 파일·경로 링크 보존, 중복 정리 차단은 합성 백업 파일로 검증했다. 기존 서비스 DB의 데이터는 변경하지 않았다.

이 회전은 위 개인 백업 저장소에서 이 도구가 관리하는 묶음에 한정한다. 예전 작업의 OS 임시 디렉터리 백업, 사용자가 다른 곳에 복사한 파일, 휴지통·디스크 복구 가능성은 관리하지 않는다. PC나 실행기가 꺼져 있는 동안에도 보관 파일이 자동 정리되는 기능은 아니다. 암호화·별도 장비 복구·운영 복원 후 삭제/파기 상태 재적용은 별도 작업이다.
