# 전체 법령정보 수집 준비 — 2026-11-18

사용자 범위: 임대차 제한 없이 법령·행정규칙·자치법규·판례와 제공되는 연혁. F 드라이브 초기화와 DB 저장 위치 변경은 보류한다. 이번 준비는 목록 점검 도구와 실행 계획이며 전체 수집기 완성을 뜻하지 않는다.

## 현재 확인 결과

- 데스크탑 `C:/dev/AURORE/local-dev/.env`의 `MOLEG_OC` 미설정. 인증값이나 원문을 출력하지 않고 설정 여부만 검사했다.
- 기존 법령 갱신기는 DB에 등록된 법령만 추적한다. 빈 DB를 전체 목록으로 채우는 최초 수집기로 사용할 수 없다.
- 기존 법령 원문 파서는 `eflaw`, 판례 파서는 `prec`에 맞춰져 있다. 행정규칙·자치법규 원문을 법령 파서에 그대로 넣지 않는다.
- 기존 판례 목록 수집은 1,000건 상한, 본문 처리는 기본 20건/회다. 전체 목록을 한 번에 요청하면 중단되므로 날짜별 분할 계획이 필요하다.
- 기존 예약 실행은 검토 자료 준비까지이며 자동 DB 반영은 하지 않는다. 데스크탑 예약을 새로 켜지 않았다.

## 인증 준비

[공식 신청 화면](https://open.law.go.kr/LSO/usrJoin.do) 또는 기존 계정의 API 관리에서 필요한 목록·본문 서비스의 신청/승인을 확인한다. 기존 노트북 인증값이 있다면 먼저 그 계정을 사용한다. 등록한 서비스와 호출 서버/IP 조건은 계정에서 확인해야 하며, 노트북에서 됐다는 이유로 데스크탑에서도 된다고 판단하지 않는다.

인증값은 데스크탑 `local-dev/.env`의 `MOLEG_OC=`에 직접 저장한다. 대화나 Git에 적지 않는다. 신청 범위는 시행일 기준 법령 목록·본문, 행정규칙 목록·본문, 자치법규 목록·본문, 판례 목록·본문, 필요한 변경이력 서비스다. 대량 호출 허용량·이용 조건·등록 IP는 계정/운영기관에서 확인한다. 이번 조사에서 확정된 초당·일일 호출 한도를 찾지 못했으므로 임의 숫자를 공식 제한으로 쓰지 않는다.

## 수집 범위와 목록 점검

목록은 `https://www.law.go.kr/DRF/lawSearch.do`, 본문은 `lawService.do`를 사용한다. 인증과 실제 응답 구조는 각 서비스별로 검증한다.

| 묶음 | 목록 target / nw | 현재 준비 상태 |
| --- | --- | --- |
| 현행 법령 | eflaw / 3 | 목록 점검, 기존 본문 파서 재사용 후보 |
| 연혁 법령 | eflaw / 1 | 목록 점검, 버전별 본문 확인 필요 |
| 시행예정 법령 | eflaw / 2 | 현행과 분리해 점검 |
| 현행 행정규칙 | admrul / 1 | 목록 점검, 본문 파서·저장 연결 필요 |
| 연혁 행정규칙 | admrul / 2 | 동일 |
| 현행 자치법규 | ordin / 1 | 목록 점검, 본문 파서·저장 연결 필요 |
| 연혁 자치법규 | ordin / 2 | 동일 |
| 판례 | prec / 해당 없음 | 기존 수집기 재사용, 목록 분할 필요 |

`nw` 숫자는 서비스별 의미가 다르다. 법령의 연혁은 1이지만 행정규칙·자치법규 연혁은 2다. `lsHistory` 가이드는 HTML만 명시하므로 JSON 범용 수집 대상으로 임의 추가하지 않는다. 판례는 API가 제공하는 공개 자료 범위이며 모든 법원의 모든 판결문을 뜻하지 않는다. 과거 정정본까지 모두 제공된다고 가정하지 않고, 제공 연혁과 향후 관측한 정정 이력을 구분한다.

저장소 루트에서 다음과 같이 점검한다.

```powershell
# 외부 요청 없는 범위·인증 설정 여부 확인
node --env-file=local-dev/.env backend/tools/collection-preflight.mjs

# 인증 설정 후 8개 묶음 각각 목록 1건만 조회 (본문·DB 변경 없음)
node --env-file=local-dev/.env --use-system-ca backend/tools/collection-preflight.mjs --probe
```

점검은 순차 요청, 요청 사이 1초 대기, 요청당 20초 제한, 응답당 2MiB 제한이다. 이는 점검 도구의 보수적인 자체 제한이며 공식 할당량이 아니다. 결과에는 건수와 크기만 남기고 원문·링크·인증값은 저장하지 않는다. `LIST_OK`는 첫 페이지 목록 응답 확인일 뿐 본문 접근·전체 수집 성공을 뜻하지 않는다. 빈 목록도 검토 대상으로 표시한다. 실제 서비스의 구조가 다르면 오류로 멈추고 공식 응답을 확인한 뒤 파서를 조정한다.

## 최초 전체 수집 구현 순서

1. 인증/등록 조건 확인 후 위 점검으로 자료별 건수 확보. 소량 본문을 받아 항목·버전·출처 검증. 분야를 임대차로 제한하지 않고 여러 법령 종류와 지자체 표본 사용.
2. 전체 목록 발견 및 체크포인트 구현. 법령은 공식 법령 ID와 시행본 일련번호·시행일을 함께 보존하고, 다른 자료는 해당 서비스 식별자와 자료 종류를 함께 보존해 번호 충돌 방지.
3. 공식 원문과 SHA-256, 조회 시각, 요청 조건(인증값 제외), 목록/본문의 식별자 일치 여부 기록. 원문·검색용 텍스트·임베딩은 분리. 첨부 별표/서식·이미지/PDF는 본문 JSON과 별도 용량/접근 검증.
4. 목록은 최대 100건/페이지로 조회하되 분할별 완료 기록 보존. 수집 중 전체 건수/페이지/ID가 달라지거나 반복되면 해당 분할을 재검토하고 중복 제거. API 목록은 고정 시점 스냅샷이 아니므로 처음과 끝의 건수 대조만으로 누락 없음을 보증하지 않음.
5. 판례는 선고일 범위를 나눠 기존 1,000건 상한 이내의 목록 생성. 한 날짜에 상한을 넘으면 공식 지원 필터(법원/출처 등)로 추가 분할하는 기능이 필요하며 결과를 잘라 버리지 않음. 선고일은 신규 등록일이 아니므로 신규 발견과 정정 탐지를 별도 설계.
6. 재시도는 네트워크·일시 서버 오류에만 제한 적용. 인증 오류는 중단, 호출 제한 응답은 지정 대기 정책 확인 후 재개. 실패 항목 보존, 단일 실행 점유, 원자적 파일 교체는 기존 수집 방식 재사용.
7. 검토한 원문을 시험 DB에서 중복 반영·버전·정정·조문 구조까지 검사한 뒤 실제 DB 반영. 행정규칙·자치법규의 코드값과 파서/저장 연결이 검증되기 전 대량 반영하지 않음. 새 스키마가 필요하면 별도 설계 변경으로 남김.
8. 최초 적재 검증 후 일일 갱신과 주기적 전체 목록 재대조. 원천에서 사라진 항목은 즉시 물리 삭제하지 않고 확인 후 상태 처리. 임베딩·AI 설명은 원문 검증 후 별도 단계로 실행.

## 저장 공간과 시작 조건

이번에는 C 드라이브에 소량 점검 결과만 두며 F 드라이브는 사용하지 않는다. 전체 수집은 저장 위치 확정 후 시작한다. 기존 PostgreSQL 원본 저장 구조를 임의로 파일 전용 구조로 바꾸지 않는다.

실제 용량은 자료별 표본 본문/첨부 크기와 전체 목록 건수, DB 인덱스, 임베딩, 백업·복구 공간을 따로 계산한다. 목록 응답 크기로 전체 본문 용량을 추정하지 않는다. 표본의 평균·큰 자료 분포와 임시 작업 공간을 포함해 산정한 뒤 F 드라이브 여유 공간과 비교한다. 백업은 운영 DB와 같은 물리 디스크에만 두지 않는다.

지금 다음으로 필요한 것은 **기존 API 계정의 인증값 설정과 서비스/접속 조건 확인**이다. 이후 목록 8건 점검 → 자료별 소량 본문 검증 → 용량 산정 → F 저장 위치 확정 → 전체 수집기 확대 순으로 진행한다.
