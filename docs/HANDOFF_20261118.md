## 내일 회사 노트북에서 할 일

1. 자신의 AURORE 폴더에서 미커밋 변경 확인 후 `git pull --ff-only origin main`. `.env`, DB, 모델, 비공개 원문과 로컬 수집 이력은 Git으로 이전되지 않는다.
2. 집 공유기 포트포워딩과 공인 IP/DDNS부터 확인. 아직 설정/외부 검증 완료가 아니다. 계획은 외부 TCP `40222` → 데스크탑 `192.168.0.3:2222`. 데스크탑 DHCP 주소 예약 필요. WAN 공인 IP/이중 NAT 여부 확인. DB·AI 포트를 공유기에 직접 열지 않는다.
3. 데스크탑이 켜져 있고 Docker/DB·AI가 실행 중인지 확인. 회사 정책에서 SSH 허용 여부 확인 후 기존 노트북 키로 연결한다. VPN은 사용하지 않는다.

```powershell
ssh -N -T -p 40222 -i "$env:USERPROFILE\.ssh\id_ed25519" -o IdentitiesOnly=yes -o HostKeyAlgorithms=ssh-ed25519 -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -L 127.0.0.1:15433:127.0.0.1:5433 -L 127.0.0.1:18001:127.0.0.1:8001 aurore_tunnel@집의공인IP또는DDNS
```

처음 접속 시 데스크탑 ED25519 서버 키 지문을 확인한다: `SHA256:kThdpzy6iWXnC8nGaAgyuw5WFqu1uVT0VA9mhC0JHkQ`.

데스크탑은 기존 노트북 공개키 `SHA256:J+J1VZX81+lDtXJ/iZfkn0jHRfJnC81nqhhORXwYa08`만 허용한다. 전용 계정 `aurore_tunnel`은 비밀번호 로그인·일반 명령 실행을 차단하고 DB와 AI 두 목적지로의 터널만 허용한다. 데스크탑 내부에서 임시 키를 사용한 DB 프로토콜 응답·AI 상태 응답·일반 명령 차단·다른 목적지 차단을 검증했으며 임시 키는 제거했다. 실제 회사 노트북 키로 외부에서 접속한 검증은 남아 있다.

4. 터널 창을 열어 둔 상태에서 `Invoke-RestMethod http://127.0.0.1:18001/health` 확인. 노트북의 AI 주소는 `http://127.0.0.1:18001`, DB 주소는 `127.0.0.1:15433`을 사용한다. DB 사용자/DB 이름과 암호는 데스크탑 설정을 따른다. 암호는 별도 안전한 경로로 옮기고 채팅·Git에 넣지 않는다.
5. 노트북의 기존 법제처 API 계정/인증값과 신청 서비스를 확인한다. 데스크탑 `local-dev/.env`의 `MOLEG_OC`는 비어 있다. 노트북 개인키는 노트북에 둔다. SSH 계정에는 일반 명령 실행 권한이 없으므로 데스크탑 환경 파일 변경은 별도 관리 경로로 해야 한다.

## 수집 준비와 다음 순서

[전체 수집 준비](FULL_COLLECTION_PREPARATION.md)에 범위·API 근거·한계를 정리했다. 새 `backend/tools/collection-preflight.mjs`는 외부 호출 없는 설정 점검과 `--probe`를 통한 8개 목록 각 1건 점검을 지원한다. 실제 API는 인증 미설정 때문에 호출하지 않았다. 합성 응답 기반 테스트는 통과했다.

인증·접속 조건 확인 → 목록별 건수 조회 → 분야별 소량 본문과 첨부 검증 → 실제 용량 산정 → F 저장 위치 결정 → 전체 수집/재개 기능 확장 순서다. 기존 수집기는 등록 법령 변경분과 선택 판례 중심이며 전체 최초 수집기, 행정규칙·자치법규 본문 수집기는 아직 완성되지 않았다. 자동 대량 수집이나 자동 DB 게시를 켜지 않았다.

## F 드라이브 판단

약 4TB의 실제 사용 가능 공간이면 텍스트 중심 수집을 시작하기에는 충분한 여유가 있을 것으로 예상한다. 첨부·전체 연혁·인덱스·임베딩·백업까지 포함한 최종 용량은 표본과 건수로 산정해야 한다. 느린 HDD/USB 디스크는 원문 보관·백업에는 적합하지만 DB의 작은 랜덤 읽기/쓰기와 인덱스 작업은 느려질 수 있다. 텍스트라는 이유로 DB 속도 영향이 사라지지는 않는다.

권장 배치는 용량이 확보된 SSD에 운영 PostgreSQL/검색 인덱스, F에 수집 원문/첨부 보관이다. 별도 백업은 다른 물리 디스크에도 둔다. 당장 SSD 공간이 부족하면 F에서 개발을 시작한 뒤 측정해 결정할 수 있으나 현재 C 여유 공간이 작아 무조건 C에 모두 유지하는 방식도 적절하지 않다. F 정리 중 속도를 정상 성능으로 판단하지 않으며, 오늘 벤치마크나 디스크 변경은 하지 않았다.
