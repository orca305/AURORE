## 2. 포트폴리오에서 강조할 이야기(문제 → 접근 → 결과)

### 2.1 "AI가 법을 지어내는 문제"를 구조로 막았다
- 문제: 일반 LLM은 존재하지 않는 조문·숫자를 그럴듯하게 쓴다. 법률 정보에서는 치명적이다.
- 접근: ① 법제처 원문 5,631개 법령(현행 조문 약 30만 건)을 해시 검증해 스냅샷으로 보관 ② 모델은 근거 번호만 고르고, **코드가 원문과 글자 단위로 대조** ③ 원문에 없는 조문 번호·숫자·단정 표현은 제거하거나 "확인되지 않음"으로 표시 ④ 근거가 없는 일반 설명에는 근거 표시를 붙이지 않음.
- 결과: 합성 홀드아웃 30문항 통과 18 → 29, 오인용 3 → 1, 법과 무관한 질문에 억지로 답한 경우 0.

### 2.2 측정 가능한 개선 루프
- 평가 도구(`backend/tools/evaluate-explanations.mjs`)로 매번 같은 방식으로 재현. 검색 개선 단계별 통과율(33 → 81/100)을 표로 남김.
- 의미 검색(bge-m3 임베딩) 기여를 분리 측정: 같은 100문항에서 어휘 검색만 66 → 의미 검색 포함 81(+15).
- 측정 중 **원문 캐시가 핵심 법령을 밀어내 후보가 사라지는 버그**를 발견해 수정(민법·형법 질문에서 엉뚱한 법령이 인용되던 원인).
- 모델 비교: 같은 50문항에서 Haiku 48 / Sonnet 48 / 로컬 12B 43. 정확도가 같고 6초 빠른 Haiku로 결정.

### 2.3 운영 가능한 서비스로 만들었다

- **관리자 콘솔**: 법령 갱신·판례 수집 검토·승인, 개인정보 보관 점검, AI 작업 상태, 모델 교체(이력·롤백), 호출 모니터링(지연·오류율·비용 추정·알림), 사용자 피드백 처리.
- **개인정보·삭제 원칙**: 질문 마스킹 후 외부 전송, 물리 삭제 없이 소프트 삭제, 비회원 대화 1개월 만료, 피드백은 작성자 식별 정보 없이 저장.

## 5. 재현·실행 방법
```powershell
# 서비스 시작(DB·Ollama·AI·백엔드·화면)
powershell -NoProfile -ExecutionPolicy Bypass -File local-dev/start-desktop.ps1
# 감시(자동 복구)

cd frontend; npx tsc --noEmit; npx eslint app

cd frontend; npx next build --webpack   # 그다음 3000 포트 프로세스를 끄면 감시가 새 빌드로 올린다
# 품질 평가(새 문항 10개로 측정하는 것이 이 프로젝트의 원칙)
EVAL_SET=<세트> AURORE_EVAL_TRACE=1 node --env-file=local-dev/.env --use-system-ca backend/tools/evaluate-explanations.mjs <결과파일> <날짜>
```

## 7. 이력서·소개 문장 후보
- 법령 원문 기반 RAG 법률 안내 서비스를 설계·구현(Next.js·NestJS·FastAPI·PostgreSQL). 근거 번호 선택 + 코드 검증으로 **인용 환각을 줄이고 홀드아웃 통과율 18/30 → 29/30**으로 개선.
- 법령 5,631개·조문 30만 건·판례 1.4만 건 수집 파이프라인(해시 검증, 중단 후 이어 받기)과 bge-m3 의미 검색을 구축, **의미 검색 도입으로 100문항 통과 66 → 81**.
- 재현 가능한 평가 도구를 만들어 단계별 개선을 수치로 관리하고, 평가 중 캐시 버그를 찾아 수정.
- 외부 모델 장애·예산 소진 시 로컬 모델 자동 전환, 관리자 콘솔(법령 갱신 승인·모델 교체·호출 모니터링·피드백)과 서비스 감시를 갖춘 운영 가능한 구조.
- Cloudflare 터널과 접속 코드 보호로 단일 PC 서비스를 안전하게 외부에 공개.

## 8. 면접 예상 질문과 답 요점
- **왜 법률인가? 틀리면 위험하지 않나?** → 그래서 "근거가 확인된 문장에만 조문 표시", 원문 해시 대조, 단정 표현 제거, "법률 자문 아님" 고지. 한계도 화면과 문서에 명시.
- **환각을 어떻게 줄였나?** → 모델이 문장을 쓰되 근거는 번호로만 고르게 하고, 코드가 원문과 대조. 원문에 없는 조문 번호·숫자는 제거/표시. 근거 없는 일반 설명에는 근거 표시를 달지 않음.
- **성능은 어떻게 검증했나?** → 평가 도구, 합성 질문 세트(개발용과 홀드아웃 분리), 단계별 표. **한계도 말한다**: 합성 질문, 표본 30~100, 법령 이름 단위 정답, 전문가 검토 없음.
- **모델은 왜 Haiku?** → 같은 50문항에서 Haiku=Sonnet(48), 로컬 12B 43. 정확도가 같고 6초 빠르고 저렴.
- **가장 어려웠던 문제?** → 법령 수가 늘수록 무관한 조문이 후보에 섞여 정확도가 떨어진 것, 그리고 캐시가 핵심 법령을 밀어내던 버그를 평가로 찾은 것.
- **운영/보안은?** → 서비스는 127.0.0.1만 열고 화면만 터널로 노출, 접속 코드 보호, 개인정보 마스킹, 소프트 삭제 원칙, 모델 호출 기록에 내용 미저장, 감시·자동 복구.
- **다시 한다면?** → 처음부터 평가 세트와 전문가 검토 절차를 만들고, 스트리밍 응답과 사용자별 사용량 제한을 넣겠다.

## 9. 정직하게 말해야 할 한계(포트폴리오에 숨기지 말 것)
- 법무 검토를 받은 약관·개인정보 처리방침이 없다. 이용 고지는 화면 문구 수준.
- 평가 질문은 직접 만든 합성 질문이고 표본이 작다. 실제 사용자 로그 기반 평가가 아니다.
- 판례 연결은 조문 번호 기준이라 주제가 어긋나는 경우가 있고, 관련 판례가 붙는 비율은 질문의 10~30% 수준(판례 보정 시도는 뚜렷한 개선이 없었다).
- 답변은 완성 후 한 번에 표시(스트리밍 없음), 평균 약 10초.
- 단일 PC 운영, 백업·장애 대응 미구축. 접속 주소별 질문 횟수 제한과 비회원 세션 생성 제한이 없어 **전체 공개는 불가**(지인 테스트까지).
- 첨부 문서 질문은 예전 로컬 방식, 자치법규(162,352건)·하급심 판례는 미수집.
- 관리자 비밀번호·키 관리, 사용자별 예산 한도는 미구현.

5. 코드 정리: 로컬 DB에만 있는 마이그레이션 적용 절차 문서화, 관리자 목록 화면의 남은 영문·서식 정리.
